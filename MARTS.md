# Витрины dbmerge — beta

Требуется dbmerge >= 2.4.1. Существующие `Handler`/`HandlerLoop` работают по-прежнему.
Новые витрины используют отдельный журнал `dbmerge_tracking` и состояние
`dbmerge_marts`: старые сигналы и прогресс обработчиков автоматически не переносятся.

## Журнал репликатора

Создайте служебную схему заранее и передайте один tracker репликатору:

```python
from dbmerge import MergeTracker
from onecdc import Replicator

# engine, odata_url и auth задаёт приложение; схема service уже существует.
with MergeTracker(engine, schema="service") as tracker:
    rep = Replicator(odata_url=odata_url, odata_auth=auth, engine=engine,
                     db_schema="source", tracker=tracker)
    try:
        rep.full_load("Catalog_Контрагенты")
    finally:
        rep.close()
```

Для CDC также задайте `exchange_name` и `queue_guid`. Перед закрытием tracker
остановите репликатор и дождитесь фоновых загрузок. Tracker принадлежит приложению.
В журнал попадают merge изменений, страницы полной загрузки и пометка пропавших
строк; нулевой результат не считается изменением. Scope — `changes`/`full_load`.
Все процессы записи источников должны использовать этот журнал: запись мимо него
не даёт витринам сигнала и не удерживает безопасную границу окна.

## Обработчик и запуск

Пример — `config/handlers/orders_by_customer.py`, отдельный раннер —
`config/runner_marts.py`. Перед запуском адаптируйте реальные имена и типы полей.
Источник примера — `orders(customer_id, amount, is_deleted_or_empty)`.
Обработчик пересчитывает **весь** агрегат активных заказов в одной транзакции,
а не суммирует только изменённые строки. Это корректно учитывает удаление и
перенос заказа между покупателями, но может быть дорого для больших таблиц.
У источника и витрины не должна быть одна и та же таблица.

`destination` и `sources` содержат бизнес-схемы: `(schema, table)`.
Параметр `schema` в `run_mart` задаёт **служебную** схему состояния, а не схему
источника. Репликатор и витрина могут работать в разных процессах, но должны
видеть один журнал. Конструктор обработчика принимает `engine`.

`run_mart(handler, tracker=tracker, run_forever=False)` выполняет один проход и
возвращает, была ли работа. В этом режиме исключения передаются вызывающему.
Постоянный цикл журналирует ошибки проходов и повторяет их. Ошибки подготовки
передаются вызывающему; пример раннера проверяет результаты фоновых задач.
Автоматически созданный tracker закрывается, переданный — нет.

## Пересборка и остановка

```python
from onecdc.marts import request_rebuild, rebuild_requested

destination = ("dwh", "orders_by_customer")
request_rebuild(engine, destination, schema="service")
pending = rebuild_requested(engine, destination, schema="service")
```

Используется штатное состояние dbmerge, без таблицы `onecdc_marts` и без сброса
чужих watermark по одному имени. При старте пересборки флаг запроса может уже
сняться: активная пересборка сохранена курсором. После ошибки она продолжается;
новый запрос, поступивший во время пересборки, не теряется. Прямое редактирование
флага SQL не заменяет API запроса с его токеном.

`request_stop()` останавливает все циклы витрин в процессе, включая созданные
после запроса. Для явного повторного запуска используйте `reset_stop()`;
уже остановленные циклы остаются остановленными. Встроенная аренда защищает
destination между процессами. Работа обработчика должна быть идемпотентной:
при сбое после коммита данных до сохранения watermark проход повторяется.
Переданные извне lease и tracker остаются ответственностью приложения.
