Вердикт

OneCDC — зрелый конвейер с честной документацией ограничений 1С, но несколько инвариантов проекта нарушены конкретными ветками кода. Это не список стиля и не «нет pool_pre_ping». Это места, где КХД расходится с источником, витрина теряет строки или очередь обмена встаёт.

Доставка

Commit данных, журнал, сигнал и Notify — разные транзакции. Повтор no-op не восстановит потерянное уведомление. Объект без ключа может быть подтверждён без сохранения.

Согласованность

$skip по живому источнику пропускает строки. No-op CDC не двигает защитную метку. Плоские бухгалтерские страницы режут набор регистратора. Новые строки группы теряются после собственного UPDATE.

Ключи и значения

Транслит склеивает имена. Составное примитивное измерение оставляет в ключе нулевой GUID. Очистка строки в 1С не доезжает, если колонки нет в пачке. Double идёт через float.

Процессы

Owner = имя плана уничтожает чужие merge. Heartbeat 90 с не отличает паузу от смерти. Два HandlerLoop одного NAME переписывают витрину без отката.

Критичность — про воздействие, не про «нашлось в diff». Высокая: потеря или искажение данных, ложные удаления, устойчивая остановка. Средняя: формат источника, ошибка конфигурации, условный риск. Низкая: эксплуатация и гигиена. «При указанных условиях» значит: ветка в коде есть, для проявления нужен формат, конкуренция или конфиг — это не рапорт о сбое на боевой базе.

Конвейер и где он рвётся

Один пакет не живёт в одной транзакции: HTTP и PostgreSQL так не умеют. Идемпотентный upsert необходим и недостаточен. Нажмите ступень — каталог оставит только связанные узлы.

Конструктор → служебные таблицы → run_once: $metadata → ReceivedNo+1 → SelectChanges → разбор → merge → журнал → сигнал → Notify. full_load ставит метку страницы до чтения. HandlerLoop двигает watermark по границе WriteTracker. FullLoadCron берёт захват и вызывает ту же выгрузку.

CDC-01

Очистка строкового реквизита в 1С не доезжает до БД: старое значение остаётся навсегда

Данные · цикл измененийподтверждено по коду
Критическая

data_reader.py 917–922, 173–189 · db_writer.py 109–112 · dbmerge.py 745–751, 1292–1374 · msg002_nomenklatura.xml пустые элементы вида <d:Артикул/>

Механизм

Парсер берёт из m:properties только строковые значения: if k.startswith('d:') and isinstance(v, str). Пустой реквизит 1С отдаёт пустым элементом (<d:Артикул/>, в записанных ответах таких сотни), xmltodict превращает его в None, и поле в запись не попадает вовсе. Дальше два этапа усиливают эффект:

  • DataObject.add_records дописывает None только тем записям, у которых поле есть у соседей по пачке. Если поле пусто у всех строк пачки, колонки в данных нет.
  • dbmerge формирует список колонок из первой записи (_get_fields_from_list_of_dict) и в фазе UPDATE пишет только эти колонки. Колонка, отсутствующая в данных, в SET не попадает.

Для чисел, дат, булевых и ссылок 1С присылает текстовое значение (0, 0001-01-01T00:00:00, false, нулевой GUID), они конвертируются и пишутся. Дефект касается ровно строковых полей — а это наименования, артикулы, комментарии, коды, PredefinedDataName, Значение_Value составных реквизитов.

Сценарий

  • В 1С у номенклатуры заполнен «Артикул» = A-100; пакет изменений доехал, в БД Artikul = 'A-100'.
  • Пользователь стирает артикул и записывает элемент. В пакете приходит <d:Артикул/>.
  • Если в этом же пакете нет другой номенклатуры с непустым артикулом, колонки Artikul в данных нет; UPDATE её не трогает; merged_on может измениться из-за DataVersion… нет — DataVersion в skip_compare_fields, поэтому строка вообще «не изменилась».
  • Результат: в КХД навсегда A-100, обработчик не вызван, last_full_load_rows_modified тоже покажет 0 — полная выгрузка страдает тем же самым.

Результат зависит от состава пачки: та же очистка «сработает», если по соседству окажется запись с непустым значением этого поля. Это делает дефект трудновоспроизводимым в тестах и незаметным в эксплуатации.

Последствия

Систематическое расхождение КХД с источником по всем строковым полям, которые когда-либо очищались. Полная выгрузка не лечит (та же ветка парсера). Витрины, фильтрующие по пустому значению, дают неверный результат; «самопроверка CDC» через rows_modified = 0 ложно успокаивает.

Что исправить

  • В _get_record_fields различать три случая: значение-строка, пустой скаляр (None или словарь с m:null="true" без m:type) и коллекция (словарь с m:type="Collection(…)"). Пустой скаляр писать явно как ''/None по типу поля из метаданных.
  • Состав колонок merge брать из метаданных объекта, а не из фактического состава пачки: тогда UPDATE всегда покрывает все известные поля.
  • Регрессия: пакет из одной записи, у которой единственное строковое поле очищено; ожидание — в БД пустая строка/NULL и сдвинутый merged_on.

Как проверить

Оффлайн: подать в read_data_entries entry с <d:Артикул/> после сохранения строки с Артикул='X' в ту же схему. Проверить значение колонки после DBWriter.save. Тесты test_noise_and_tombstones.py этот случай не покрывают: там сравниваются только равные значения и сокращённый набор.

CDC-02

Второй процесс с тем же планом обмена стирает реестр незавершённых merge первого — витрина теряет строки

Обработчики · граница окнаподтверждено по коду
Критическая

write_tracker.py 97, 149–167, 169–186, 217–223 · replicator.py 532 · full_load_claim.py 24–30 (правильный образец owner) · test_handlers.py 696–715 (test_restart_forgets_own_stale_writes закрепляет поведение)

Механизм

WriteTracker получает owner = exchange_name — имя плана обмена без хоста, pid и случайного суффикса. Конструктор вызывает _cleanup(), который удаляет все строки этого owner как «остатки прошлого запуска». У соседнего механизма — FullLoadClaim — авторы уже сделали owner уникальным на экземпляр (exchange:host:pid:hex) ровно по этой причине; реестр merge этот урок не получил.

Три следствия одного решения:

  • живые строки первого процесса удаляются при старте второго;
  • счётчик id = f'{owner}:{n}' в обоих процессах начинается с нуля — возможна коллизия первичного ключа и падение track();
  • heartbeat() продлевает все строки с owner, то есть чужие тоже — брошенная строка умершего процесса-тёзки не протухнет никогда, пока жив второй.

Сценарий

  • Процесс A (репликатор) пишет толстую страницу полной выгрузки регистра; в onecdc_writes_in_process его строка держит границу окна на started_at.
  • Стартует процесс B с тем же exchange_name: второй контейнер при rolling update, отдельный контейнер с FullLoadCron (рекомендуемая документацией раскладка), ручной run_once рядом с работающим run_forever.
  • _cleanup() процесса B удаляет строку A. Обработчик считает boundary = now(), обрабатывает окно и записывает last_run_at.
  • A коммитит merge; merged_on его строк — время начала транзакций UPDATE/INSERT, левее уже записанного last_run_at.
  • Инкремент merged_on > last_run_at эти строки не увидит никогда. Сырая таблица выглядит здоровой, витрина — нет.

Последствия

Молчаливая потеря строк витрины в штатной, описанной в README раскладке «репликатор и расписание в разных контейнерах одного плана». Тот же owner ломает и отметку страницы полной выгрузки (page_started_at берётся из той же границы): снимок может затереть свежее изменение.

Что исправить

  • Owner уникальный на экземпляр по образцу FullLoadClaim; свои строки прошлого запуска не чистить по имени, а полагаться на MERGE_HEARTBEAT_TTL и MERGE_ABANDONED_TTL.
  • Опционально advisory lock на (schema, exchange_name) для режима «ровно один репликатор на план».
  • Переписать test_restart_forgets_own_stale_writes: два живых трекера одного плана не вправе удалять чужие свежие строки.

Как проверить

Оффлайн, без 1С: открыть track() в одном трекере, создать второй с тем же owner, вызвать boundary() из HandlerLoop между cleanup и выходом из track(). Ожидание: граница прижата к started_at; факт: now().

CDC-03

Транслитерация неинъективна: разные объекты и поля 1С молча попадают в одну таблицу или колонку

Имена · схема БДподтверждено по коду
Критическая

name_mapper.py 3–18, 47–61, 63–94 · data_reader.py 201–206 (dict(zip) оставляет последнее) · full_load_keys.py 43–49 (байтовое усечение есть только здесь) · PLAN.md 118

Механизм

Таблица замен отображает е и э в e, ъ и ь в пустоту, кириллическое имя может совпасть с латинским (Ёлка → Yolka). Хэш добавляется только при превышении 63 символов или совпадении со служебным именем — уже после транслита, то есть от транслита, а не от оригинала, и всего 4 hex-символа (16 бит). Проверка «ambiguous» есть лишь в обратном разрешении имени (resolve_object_name) и не защищает обычный путь CDC: map_object_name к этому моменту уже записал оба объекта в одну таблицу.

Отдельно: длина считается в символах (len(name)), а PostgreSQL ограничивает идентификатор 63 байтами. Буквы вне таблицы (украинские і ї є ґ, белорусская ў, любая латиница с диакритикой) остаются многобайтовыми: Catalog_ + 60×і — 63 символа и 113 байт. Соседний модуль full_load_keys режет по байтам — два правила в одном пакете.

Третий канал: поле 1С, чей транслит точно совпал со служебным именем (merged_on, is_deleted_or_empty, exchange_message_no), проходит ветку «это наше поле» без хэша и конфликтует с колонкой, которой управляет dbmerge или парсер.

Сценарий

from onecdc.name_mapper import NameMapper
m = NameMapper()
m.map_object_name('Catalog_Сер') == m.map_object_name('Catalog_Сэр')     # 'Catalog_Ser'
m.map_field_name('Объект') == m.map_field_name('Обьект')                  # 'Obekt'
len(m.map_object_name('Catalog_' + 'і'*60).encode())                    # 113 байт

Два объекта плана обмена с именами, различающимися только е/э или ъ/ь, после первого пакета лежат в одной таблице; scoped-mark и mark_missing одного объекта помечают строки другого. Два поля одной таблицы с одинаковым транслитом: dict(zip(out_keys, row)) оставляет значение последнего.

Последствия

Смешение данных двух объектов, ложные пометки удаления, падение CREATE TABLE/рефлексии на длинных не-русских именах. Обнаружить постфактум трудно: имена в БД выглядят правдоподобно.

Что исправить

  • Вести множество занятых идентификаторов на схему; при коллизии добавлять хэш оригинального имени (8–10 hex), а не транслита.
  • Считать длину в байтах UTF-8 общей функцией с full_load_keys; расширить таблицу транслита на украинский/белорусский алфавиты.
  • Служебные имена: любое поле 1С, транслит которого совпал с ними, хэшировать всегда — «своё» служебное поле добавляет не парсер данных, а writer.
  • Тесты на пары выше: сейчас NameMapper не покрыт ни одним тестом.

Как проверить

Оффлайн: сниппет выше. Против живой 1С: два справочника с именами «Сер»/«Сэр» в плане обмена.

CDC-04

Полная выгрузка не вставляет новые строки группы, если в той же странице обновилась существующая строка этой группы

Полная выгрузка · guardподтверждено по коду
Высокая

db_writer.py 154–160, 239–248 · replicator.py 885, 927–929 · dbmerge.py 632–666 (UPDATE коммитится до INSERT), 1183–1224, 1292–1374 · test_version_guard.py 23–26 (NEW_RUN = 2100 год скрывает дефект)

Механизм

Для регистров и табличных частей в режиме полной выгрузки DBWriter.save передаёт три условия: update_condition = merged_on < page_started_at, delete_condition = scoped ∧ merged_on < page_started_at и insert_condition = NOT EXISTS (строка той же группы с merged_on ≥ page_started_at). Отметка page_started_at берётся до чтения страницы.

dbmerge.exec выполняет фазы последовательно: UPDATE (и коммит), затем INSERT. Фаза UPDATE штампует изменённым строкам merged_on = now(), то есть значение позже page_started_at. Фаза INSERT видит эти собственные строки как «группу, переписанную после отметки», и insert_condition отбрасывает все новые строки этой группы.

Тесты guard'ов используют NEW_RUN = datetime(2100,1,1): любой now() меньше 2100 года, поэтому в тестах собственный UPDATE группу не «греет». В рабочем коде отметка — реальное время за секунды до merge.

Сценарий

  • В БД табличная часть документа D: строки 1, 2 (обе с merged_on старше прогона).
  • В 1С у строки 1 поменяли количество и добавили строку 3; изменение в обмен не попало (для этого и нужна сверка).
  • Полная выгрузка читает D одной страницей: [1', 2, 3].
  • UPDATE: строка 1 обновлена, merged_on = t₁ > page_started_at.
  • INSERT: для строки 3 условие NOT EXISTS(g.Ref_Key = D ∧ g.merged_on ≥ page_started_at) ложно из-за строки 1. Строка 3 не вставлена.
  • Отчёт прогона: rows_modified = 1, finished_at проставлен, last_full_load_dt записан. Строка 3 появится только на следующей полной выгрузке (тогда строка 1 уже равна источнику, UPDATE не сработает, группа «холодная»).

То же для набора движений регистра: перепроведённый документ с изменённой суммой и добавленным движением.

Последствия

Полная выгрузка — заявленный способ «выровнять данные», но один прогон не сходится: результат сходится только за два прогона при неизменном источнике. Метрика last_full_load_rows_modified и самопроверка «должно быть 0» становятся неверными. В бухгалтерском регистре, где окно читается целиком, эффект тот же.

Что исправить

  • Исключать из _group_not_touched_since строки, изменённые этим же merge: например, сравнивать не с page_started_at, а с отметкой, взятой после собственной фазы UPDATE, либо помечать группы, которые прогон сам обновил, и пропускать guard для них.
  • Проще: выполнять для группы один атомарный шаг «если группа холодная — заменить целиком (delete-mark + upsert)», а не три независимых условия.
  • Регрессия с реальной отметкой (db_now() за миг до сохранения), а не с 2100 годом: группа с изменённой и добавленной строкой в одной странице.

Как проверить

Оффлайн против PostgreSQL: сохранить группу [1,2] обычным save; затем save([1', 2, 3], full_load_started_at=writer.db_now()). Ожидание — три живые строки; факт — строка 3 отсутствует.

CDC-05

Пометка пропавших строк по $skip-страницам объявляет живые строки удалёнными: изменяемый источник и неуникальная сортировка

Полная выгрузка · пометка пропавшихподтверждено по коду
Высокая

replicator.py 804–836 (recheck только при окнах), 943–951, 1170–1212 · data_reader.py 339–378 ($orderby по Ref_Key → автоупорядочивание по представлению) · full_load_keys.py 111–164 · DESIGN.md 474–486, 513–545 · test_full_load.py 956 (test_run_without_any_window_does_not_recheck закрепляет отсутствие перепроверки)

Механизм

Ключи страниц копятся в таблице прогона, и после последней страницы всё, чего там нет, помечается is_deleted_or_empty. Перепроверка кандидата запросом в 1С делается только если прогон шёл окнами (recheck = date_filter is not None or windowed). Сплошной прогон «в одну выборку» перепроверки не делает — а именно у него две независимые причины пропустить живую строку:

  • Изменяемый источник. $skip=N — смещение в заново построенной выборке. Удаление или переезд в сортировке любой строки из уже прочитанного префикса сдвигает следующую страницу на одну позицию: живая строка не прочитана ни в одну страницу.
  • Неуникальный ключ сортировки. Для справочников и документов $orderby=Ref_Key 1С разворачивает в автоупорядочивание по представлению (наименование/код). Одинаковые наименования — обычное дело (номенклатура в разных группах, контрагенты-тёзки). Порядок внутри такой ничьей СУБД 1С не гарантирует между запросами (особенно при параллельных планах), и страницы дают дубли и пропуски даже без единого изменения в источнике. Авторы измерили именно это на табличной части (87 строк: 4 дубля, 5 потерь) и починили добавлением LineNumber — но у справочника тай-брейкера нет.

Сценарий

источник: [A, B, C, D], страница 1 = [A, B]
удалён A (или B переименован и уехал вниз)
страница 2: $skip=2 над [B, C, D] → [D]
C не попал в таблицу ключей; merged_on у C старый; recheck=False
mark_missing → C помечен удалённым, ресурсы обнулены, merged_on поднят → витрина пересчитана «без C»

Для справочника в 10⁵ строк со сплошным чтением (даты нет, окон нет) вероятность события пропорциональна числу страниц и активности пользователей ночью — и она ненулевая при каждом ночном прогоне.

Последствия

Ложные удаления в КХД с поднятым merged_on: витрина «увидит» удаление и пересчитает агрегаты без живой строки. Возврат — только следующей полной выгрузкой, если строка не изменится в 1С. Ошибка необратима для внешних приёмников (отправка события об удалении).

Что исправить

  • Перепроверять всех кандидатов запросом по ключу всегда, а не только при окнах — цена пропорциональна числу кандидатов, а их обычно мало.
  • Сохранять подтверждённые живые строки (перепроверка их читает) через save с guard, а не только дописывать ключи.
  • Документировать, что источник не даёт snapshot isolation, и что сплошной $skip по справочнику допустим только с перепроверкой.
  • Для сущностей добавлять в $orderby детерминированный тай-брейкер, если 1С его принимает (например, Code), и проверить поведение на живой базе.

Как проверить

Оффлайн с фейковым сервером: две страницы, между запросами убрать первую строку из выдачи; проверить, что живая строка не помечена. Сейчас test_run_without_any_window_does_not_recheck утверждает противоположное поведение как желаемое.

CDC-06

Игнорирование «шума» лишает снимок защиты: no-op пакет не обновляет метку, и устаревший снимок затирает подтверждённое состояние

Полная выгрузка · guardподтверждено по коду
Высокая

db_writer.py 116–125, 167–180, 219–237 · replicator.py 863–919 · README_DB.md 171–175

Механизм

Guard полной выгрузки опирается только на merged_on, а merged_on по замыслу двигается лишь при изменении бизнес-значений (exchange_message_no и DataVersion в skip_compare_fields). Значит «строку никто не переписывал после отметки страницы» и «строку никто не подтверждал после отметки» — разные факты, а guard проверяет первый, хотя нужен второй.

Сценарий

t0  БД: A                          источник: A
t1  источник: B                     (изменение ещё в очереди)
t2  full_load читает страницу: B    (page_started_at = t2⁻)
t3  источник снова A
t4  CDC получает пакет с A → значения равны → no-op → merged_on не тронут → пакет подтверждён
t5  full_load сохраняет B: merged_on(t0) < page_started_at → guard пропускает → БД: B

В очереди 1С последнего A уже нет. Контрпример не требует ни двух процессов, ни нарушения порядка пакетов. Симметрично: no-op CDC не защищает живой ключ от ошибочной пометки в mark_missing (та же _older_than_run).

Последствия

Полная выгрузка, призванная сверять данные, вносит устаревшее значение поверх актуального, и ни один сигнал об этом не приходит. Вероятность растёт с длительностью прогона (часы на больших регистрах) и активностью правок «туда-обратно» (проведение/отмена проведения).

Что исправить

  • Разделить два времени: merged_on (изменение значений — для витрин) и отдельная отметка последнего подтверждённого наблюдения CDC (seen_on), обновляемая и при no-op. Guard'ы и _older_than_run должны сравниваться со второй.
  • Дешёвый вариант: в режиме изменений всегда писать exchange_message_no (он не в compare, но в update — dbmerge это умеет только если строка «изменилась»), то есть нужен отдельный UPDATE по ключам пакета для no-op строк.

Как проверить

Оффлайн: последовательность save(A), save(A, emn=2) (no-op), save(B, full_load_started_at=t между ними). Ожидание — A; факт — B.

Механизм

В ветке by_period непостоянный HTTPError превращается в exhausted=False — «сузьте окно». _load_by_windows учитывает этот флаг только в цикле шагающих окон; у верхнего открытого окна (read(anchor, None)) и у хвоста (read(None, cursor)) возвращаемое значение игнорируется.   • Проверять StopSignal между окнами и страницами; не завершать прогон и не помечать пропавших, пока все окна не прочитаны.
  • Для окна, не влезающего в 1С даже за день, добавить дробление по Recorder_Type или по часам внутри суток.

Как проверить

Оффлайн: read_accounting_register, отвечающий 500 на первый вызов; проверить, что full_load не возвращает успех. Для цикла — mock, всегда отвечающий 500, и таймер.

CDC-11

Окна по периоду режут набор регистратора бухгалтерии, а writer заменяет группу целиком: страницы помечают строки друг друга

Полная выгрузка · регистр бухгалтериипри указанных условиях
Высокая

replicator.py 790–802, 885–891 · data_reader.py 401–438 · db_writer.py 139–162, 270–287 · metadata_reader.py 305–320 (object_key регистра = Recorder + Recorder_Type)

Механизм

Для регистров, подчинённых регистратору, окно строится лямбдой RecordSet/any(…) и отдаёт набор целиком — на этом держится scoped-пометка «строки группы, которых нет в странице, выпали из набора». Регистр бухгалтерии читается иначе: из виртуальной таблицы RecordsWithExtDimensions(Condition='Period ge … and Period lt …'), которая возвращает плоские движения, отфильтрованные по периоду. Если у одного регистратора движения лежат в разных окнах (или пользователь задал период, отсекающий часть набора), страница несёт часть группы, а _scoped_delete_condition по (Recorder, Recorder_Type) помечает остальные движения регистратора как выпавшие.

Guard merged_on < page_started_at не спасает: свежее окно загружается первым, а старое — следующим, и строки свежего окна к тому моменту старше отметки новой страницы? Нет — они новее, поэтому защищены. Но обратная сторона верна: движения старого окна, уже лежащие в БД от прошлых прогонов, помечаются страницей свежего окна.

Сценарий

Документ «Операция» с проводками за 31.03 23:50 и 01.04 00:10 (один регистратор, два периода). Окна: [01.04, +inf) и [02.03, 01.04). Первое окно приносит только апрельскую проводку; scoped-mark помечает мартовскую (из БД) удалённой и гасит суммы. Второе окно приносит мартовскую и «воскрешает» её — но с новым merged_on, лишним сигналом и ложными событиями для внешних приёмников; при обрыве между окнами — ложная пометка остаётся.

Последствия

Ложные пометки и обнуления ресурсов бухгалтерских проводок; в промежутке между окнами витрина считает по искажённым данным. Условие достижимости — регистратор с движениями в разных периодах; платформа этого не запрещает, код не проверяет.

Что исправить

  • Для плоских бухгалтерских окон использовать upsert без scoped-пометки, а исчезновение движений определять единым проходом mark_missing по всему окну прогона.
  • Либо дочитывать полный набор регистратора (read_by_key) для регистраторов, встретившихся у края окна.

Как проверить

Оффлайн: подать в DBWriter.save два «окна» одного регистратора с full_load_started_at и проверить флаги между ними.

CDC-22

Таймаут или обрыв на странице не уменьшает страницу, а фоновая выгрузка перезапускается с нуля каждый цикл без backoff

Полная выгрузка · устойчивостьподтверждено по коду
Средняя

replicator.py 895–919 (только HTTPError), 1599–1610, 1612–1625 · metadata_reader.py 25

Механизм

Адаптация размера страницы срабатывает только на requests.HTTPError. ReadTimeout, ConnectionError, обрыв по Content-Length — исключения других классов: они пробрасываются, прогон падает, а _full_load_page_size остаётся прежним. _run_full_load оставляет full_load_is_required, и следующий цикл (через interval, обычно 60 с) начинает объект заново с skip=0 и тем же размером страницы. Ни счётчика неудач, ни паузы, ни точки возобновления. _dispatch_full_loads при этом захватывает сразу все помеченные объекты, даже если воркеров два: остальные ждут в очереди с активным захватом, недоступные расписаниям других процессов.

Сценарий

Регистр с толстыми наборами: страница адаптировалась до 30 entry, но одна entry на 12 МБ формируется 1С дольше 15 минут → ReadTimeout → прогон упал на 40-й странице → через минуту всё с начала, те же 39 страниц, тот же таймаут. Сутки непрерывной нагрузки на 1С без единой полезной записи после 39-й страницы.

Последствия

Бесконечная тяжёлая нагрузка на сервер 1С, отсутствие прогресса и невидимость проблемы (в логе — одна строка ошибки в час).

Что исправить

  • Ловить requests.RequestException (не только HTTPError) и делить страницу так же, как при 500.
  • Экспоненциальный backoff и предел попыток для фоновой выгрузки объекта; фиксировать прогресс (последнее успешно прочитанное окно) и возобновлять с него.
  • Захватывать объект в момент фактического старта воркера, а не при постановке в очередь.

Как проверить

Оффлайн: mock read_object, бросающий ReadTimeout на N-й странице; проверить размер страницы и число повторов.

Замысел и его граница

DESIGN.md: «В run_forever упавшая фоновая выгрузка повторится на следующем цикле — и начнёт уже с подобранного размера». Тезис верен только для отказов с HTTP-кодом; для таймаутов подобранный размер не меняется. Оспорено.

CDC-07

Сбой между commit merge и сигналом теряет уведомление обработчику; повтор пакета его не восстанавливает

Высокая

Механизм

Merge, завершение строки журнала, снятие строки реестра и сигнал обработчику — четыре отдельные транзакции (а внутри merge — ещё три коммита dbmerge). Если процесс падает или БД отказывает после коммита данных, но до HandlerSignals.signal, пакет не подтверждён и придёт снова. Но повторный merge увидит уже записанные значения: rows_modified = 0, added_fields = {}, и _signal_handlers ничего не поставит. Затем пакет будет подтверждён.

Тот же разрыв на каждой странице полной выгрузки и у request_full_rebuild: новая колонка добавлена, DDL закоммичен, а требование пересборки не записано — повтор колонку заново не «добавит».

Сценарий

  • save(Document_X) закоммичен: строки обновлены, merged_on = t.
  • Обрыв соединения на write_result или signal; исключение; пакет не подтверждён.
  • Следующий цикл: тот же пакет, merge no-op, сигнала нет, подтверждение отправлено.
  • Обработчик не вызван. Он увидит строки с merged_on = t только при следующем сигнале по любой подписанной таблице — которого может не быть часами.

Последствия

Витрина/внешний приёмник отстаёт на неопределённое время; при enabled=false/паузе обработчика сигнал теряется совсем. Нарушено обещание «репликатор знает, когда данные изменились, и сам вызывает ваш код».

Что исправить

  • Сделать сигнал долговечной обязанностью: ставить update_requested_at в той же транзакции, что и последняя фаза merge (dbmerge допускает commit_all_steps=False, но коммитит сам; нужен хук или вынесение сигнала в outbox-таблицу, которую разбирает отдельный шаг «до подтверждения пакета»).
  • Минимум: сигналить подписчикам всех таблиц пакета до NotifyChangesReceived, независимо от rows_modified, если предыдущая попытка обработки пакета этого номера не завершилась (признак — незакрытая строка журнала с тем же message_no).

Как проверить

Оффлайн: подменить HandlerSignals.signal исключением на первом вызове, прогнать run_once дважды; проверить update_requested_at подписчика.

CDC-16

Высокая

Механизм

HandlerSignals кэширует список подписчиков (только enabled) на SUBSCRIPTIONS_TTL = 30 с. Что исправить

  • При регистрации/включении ставить себе update_requested_at = now() (catch-up) и инвалидировать кэш репликатора (версия подписок в таблице).

Как проверить

Оффлайн: HandlerSignals с прогретым кэшем, регистрация нового HandlerLoop, signal() в пределах 30 с — метки нет.

Замысел и его граница

DESIGN.md обосновывает кэш экономией запросов «на каждую страницу полной выгрузки» — резонно, но окно потери сигнала при регистрации документ не обсуждает. Про enabled README_DB утверждает, что окно не копится; код показывает обратное. Оба тезиса оспорены.

CDC-17

Пакет только из неподдерживаемых объектов зацикливает очередь; смешанный пакет теряет их безвозвратно; дроссель переносит классы, которых Python не знает

Цикл изменений · поддержка классовподтверждено по коду
Высокая

data_reader.py 831–863 · replicator.py 588–591 · metadata_reader.py 81–89 · onecdc-throttle-module.txt 171–201 (константы и регистры расчёта переносятся в очередь отдачи) · DESIGN.md 372–382

Механизм

Парсер пропускает классы вне SUPPORTED_TYPES с одним WARNING на пакет. Подтверждение шлётся только при len(self.changes) > 0. Отсюда два разных исхода одного явления: смешанный пакет подтверждается (регистрации неподдержанных объектов потеряны), пакет из одних неподдержанных — не подтверждается и повторяется каждый цикл с тем же MessageNo. Дроссель на стороне 1С при этом сознательно переносит в очередь отдачи константы и регистры расчёта; заполнив лимит ЛимитОчереди() такими регистрациями, он закупоривает очередь для поддерживаемых объектов, а Python-сторона их только повторяет.

  • Регламентное задание переносит 500 регистраций регистра расчёта (закрытие месяца по зарплате).
  • onecdc читает пакет: все entry неподдержанные, changes пуст, notify нет.
  • Каждые 60 с — тот же SelectChanges на 500 объектов; очередь B полна, новые справочники в неё не переносятся; репликация всего плана стоит, в логе только WARNING.

Последствия

Остановка репликации плана целиком либо потеря изменений неподдержанных классов — в зависимости от состава пакета; поведение не соответствует ни документации, ни ожиданиям оператора.

Что исправить

  • Единая политика: считать число исходных entry отдельно от числа сохранённых объектов; для пакета с неподдержанными классами — либо явный «карантин» с подтверждением и записью в журнал, либо остановка с ERROR, но одинаково для обоих случаев.
  • Согласовать ОбъектыОбхода дросселя с SUPPORTED_TYPES; на старте сверять состав плана (через ExchangePlan_*/метаданные) и предупреждать о классах вне поддержки.

Как проверить

Оффлайн: пакет только из CalculationRegister_*; проверить, что notify не шлётся и цикл повторяет номер.

Замысел и его граница

DESIGN.md сознательно выбирает «пакет всё равно подтверждается, решение принимает человек» — с этой политикой для смешанного пакета можно согласиться как с осознанным компромиссом. Но код не реализует её для пакета только из неподдержанных объектов (там подтверждения нет, и очередь зацикливается), а собственный 1С-модуль проекта создаёт именно такие пакеты. Находка сохранена как расхождение кода с заявленным замыслом.

Что исправить

CDC-08

Истечение heartbeat принимается за доказательство rollback: живая, но замедленная транзакция теряет защиту границы и захвата

Процессы · отметки живостипри указанных условиях
Высокая

write_tracker.py 26–40, 196–215 · full_load_claim.py 44–53, 80–110 · replicator.py 1612–1625 · metadata_reader.py 578–597 · README_DB.md 343–350, 377–381

Механизм

Граница окна и захват объекта исключают строки, у которых heartbeat_at старше 90 с. Документация формулирует это как «транзакции умершего процесса СУБД уже откатила». Но отсутствие отметки 90 секунд не отличает мёртвый процесс от живого, который: ждёт блокировку в PostgreSQL, стоит на GC/паузе контейнера, исчерпал пул соединений (сами авторы описывают этот случай), потерял одно соединение из-за сетевого сбоя при живых остальных. Fencing'а нет: потерявший lease процесс продолжает писать и после «перехвата».

Сценарий

  • Граница. Merge A застрял на 3 минуты (блокировка на целевой таблице от чужого CREATE INDEX обработчика). Heartbeat-поток не получил соединения из пула (все у страниц выгрузки). boundary() исключает строку A, обработчик двигает last_run_at. A дописывает строки с merged_on левее — они потеряны для инкремента, хотя сигнал придёт.
  • Захват. Полная выгрузка объекта идёт 2 часа; heartbeat не продлился 90 с; расписание в другом контейнере захватывает объект и начинает вторую выгрузку. Первый процесс, не проверяя владение, дочитывает свои страницы и вызывает mark_full_loaded; оба пишут rows_modified и метрики поверх друг друга; 1С делает двойную работу.

Последствия

Потеря строк витрины и двойная нагрузка на 1С в условиях, которые документация относит к «эксплуатационным» (нехватка пула), но которые не сигнализируются ничем, кроме постфактум расхождений.

Что исправить

  • Для границы: держать реестр в той же транзакции, что merge, или брать её из pg_stat_activity/advisory lock живой сессии — истёкший heartbeat может отсекать строку только когда сессия-владелец точно отсутствует.
  • Для захвата: fencing token (номер эпохи в onecdc_metadata_objects), проверяемый перед каждой записью страницы и в mark_full_loaded; при потере lease — прервать прогон.
  • Отдельное соединение (или отдельный пул) для heartbeat-потоков, чтобы дефицит пула не превращался в ложную смерть.

Как проверить

Оффлайн: держать track() открытым дольше 90 с с заблокированным heartbeat (mock) и проверить, что boundary() его перешагивает; затем закоммитить merge и убедиться, что строки левее last_run_at.

CDC-26

Реестр объектов синхронизируется с удалением, а словарь метаданных мутируется под чужими потоками: стираются захват и состояние, возможен RuntimeError

Метаданные · реестрподтверждено по коду
Средняя

Механизм

Три независимых слабости одного жизненного цикла:

  • _fetch_and_parse_metadata только добавляет ключи в self, никогда не удаляя; поэтому объект, пропавший из $metadata, остаётся в памяти до рестарта и в _sync_objects(list(self.keys())). Обещанное «пропавшие удаляются из реестра» до рестарта не выполняется.
  • Зато после рестарта _sync_objects с delete_mode='delete' удаляет строку вместе с last_full_load_dt, full_load_is_required, full_load_owner и full_load_heartbeat_at. Синхронизация вызывается лениво из любого потока при незнакомом поле, то есть и во время чужой выгрузки: временное исчезновение объекта из публикации (перенастройка состава OData внешней обработкой проекта, обновление конфигурации) стирает живой захват — heartbeat/release обновляют 0 строк, следующая синхронизация вставляет строку с пустым владельцем, и второй процесс захватывает объект параллельно первому; mark_full_loaded обновляет 0 строк, история выгрузки теряется.

Дополнительно is_loaded = True ставится до _sync_objects: при её отказе следующий run_once считает метаданные загруженными и работает с objects_table = None; пустой $metadata оставляет objects_table = None, и list_full_load_required падает на None.c. Сценарий

Администратор выполняет в внешней обработке «Включить план и его объекты в OData»: состав переустанавливается целиком; в это время $metadata на секунды отдаёт неполный список; репликатор, встретив новое поле, перечитывает метаданные и удаляет из реестра половину объектов вместе с их захватами и отметками. Через минуту объекты возвращаются «новыми» и уходят в повторную полную выгрузку.

Последствия

Потеря состояния выгрузок (дорогие повторы), двойные выгрузки, спорадические падения страниц.

Что исправить

  • Собирать новый словарь отдельно и публиковать атомарной заменой ссылки; is_loaded — только после успешной синхронизации.
  • Реестр: не удалять строки, а помечать «отсутствует в $metadata с …»; захват и отметки не трогать никогда автоматически.
  • Читателям брать снимок (list(self.metadata) под тем же lock) либо использовать неизменяемые словари.

Как проверить

Оффлайн: test_metadata_objects.py зовёт _sync_objects напрямую; добавить повторный разбор двух разных $metadata и параллельную итерацию.

После старта цикла остановка ждёт конца итерации, а with ThreadPoolExecutor — завершения всех уже поставленных в очередь выгрузок (в очередь ставятся все помеченные объекты сразу); ни страницы, ни окна StopSignal не проверяют. Итерация может длиться 15 минут только на SelectChanges (read timeout), а очередь выгрузок — часы; stop_grace_period: 60s в примере гарантирует SIGKILL с незакрытыми merge и строками реестра до TTL. Конструкторы библиотеки к тому же заменяют обработчики сигналов приложения-хозяина без цепочки вызовов.

Сценарий

Rolling update при очереди из 12 объектов на первичную выгрузку: SIGTERM → «Replication loop stopping, waiting for full loads to finish» → через 60 с SIGKILL посреди merge → staging-таблица и строка реестра остаются, страницы перечитываются заново после рестарта.

Последствия

Непредсказуемое время остановки, «грязные» остатки в БД, невозможность корректно остановить процесс до первого цикла.

Что исправить

  • Процессное событие остановки, наследуемое новыми циклами; отмена не начатых futures (cancel_futures=True) и проверка stop между страницами/окнами без объявления прерванной выгрузки успешной.
  • В примере compose — stop_grace_period, согласованный с реальной семантикой, и документация.
  • Не ставить обработчики сигналов в конструкторах библиотечных классов; предоставить явный install_signal_handlers() для точки входа.

Как проверить

Оффлайн: отправить SIGTERM процессу до run_forever, затем запустить цикл — он не остановится.

Замысел и его граница

stop_signal.py подробно объясняет, почему перехват ставится в конструкторах (ThreadPoolExecutor и рабочие потоки). Аргумент принимается для контейнера; но он не объясняет ни потерю раннего сигнала, ни ожидание всей очереди. Тезис «останавливаемся после текущей итерации» оспорен: фактически — после всей очереди.

CDC-45

ON_FULL_LOAD=False отключает и сигналы об удалениях, которые находит только полная выгрузка

Обработчики · семантика ON_FULL_LOADподтверждено по коду
Низкая

replicator.py 1204–1211 · handlers.py 540–556

Механизм

Пометка пропавших строк сигналит с источником full_load; подписчик с ON_FULL_LOAD=False её не получает. Физические удаления обнаруживаются исключительно полной выгрузкой, поэтому обработчик-отправщик, отказавшийся от бэкфилла, узнаёт об удалениях лишь тогда, когда случайный сигнал по другой таблице откроет окно, в которое эти строки попадут (их merged_on поднят).

Сценарий

Отправка изменений в очередь сообщений с ON_FULL_LOAD=False: удаления доходят с задержкой до следующего живого изменения любой подписанной таблицы.

Последствия

Задержка событий удаления для внешних приёмников; данные не портятся.

Что исправить

  • Отдельный источник сигнала full_load_marking, не фильтруемый флагом бэкфилла.

Как проверить

Оффлайн: _mark_missing_rows с подписчиком on_full_load=False.

Замысел и его граница

Единый фильтр по источнику обоснован тем, что обработчик не различает источники по метке; граница замысла — объединение бэкфилла и обнаруженного удаления в один источник.

Порядок исправлений

Рекомендация «один процесс + HTTPS + ночной full_load» не закрывает no-op guard, потерю сигнала, OFFSET-пометку и разрезанные группы. До правок каждую из этих гарантий нужно считать ограниченной сценариями ниже.

Что принято как замысел

Не всё из каталога — «баг против авторов». Ниже — решения, которые код и DESIGN.md объясняют, и которые этот отчёт не оспаривает целиком. У каждого есть граница: она вынесена в связанную находку.

  • Страницы только через $skip, keyset-курсора нет — На замерах показано, что ссылку нельзя сравнивать оператором «больше», а $orderby по ссылке — автоупорядочивание; keyset был бы неверен. Принято; цена глубины лечится окнами по периоду.
  • Окна только сужаются, размер страницы после отказа только опускается — Обосновано «пилой» 500 → успех → 500 и стоимостью перечитывания. Принято.
  • Открытая верхняя граница при date_from=timedelta — Документы с датой в будущем должны попадать в окно; менять умолчание нельзя без смены контракта. Принято; для точного периода задаются обе границы.
  • Удаления независимого регистра и физические удаления — только через полную выгрузку — В OData-выборке обмена понятия «объект удалён» нет; сверка — единственное место. Принято как ограничение; следствие для env-режима без расписаний — в условиях эксплуатации.
  • Подтверждение смешанного пакета с неподдерживаемыми классами — Осознанная политика «состав плана — ответственность человека». Принята для смешанного пакета; расхождение для пакета только из неподдерживаемых объектов — CDC-17.
  • Метка сигнала вместо очереди событий — Обработчик строит текущее состояние по окну; промежуточные состояния не нужны. Принято с оговоркой: для event log/RabbitMQ нужна иная модель.
  • Образ ставит пакет с PyPI, а не из дерева — Версия образа равна версии пакета; собрать локальные правки нельзя — так задумано. Принято.
  • Отсутствие параметра verify/TLS — Корпоративный CA задаётся REQUESTS_CA_BUNDLE/CURL_CA_BUNDLE; проверка сертификата включена по умолчанию. Дефекта нет.
  • xmltodict без defusedxml — xmltodict 1.0.x по умолчанию отключает внешние сущности; XXE/billion laughs не доказаны. Неограниченный объём обычного XML — CDC-18.
  • Перехват сигналов в конструкторах — Обоснование про ThreadPoolExecutor принято для контейнера; оставшиеся дефекты остановки — CDC-27.
  • Изменяемый default records=[] в DataObject — Список не мутируется; вопрос стиля, не дефект.
  • Отсутствие requests.Session и HTTP-ретраев — Повторы есть на уровне циклов и страниц; слепые ретраи POST SelectChanges/Notify опасны неоднозначным результатом. Улучшение, не дефект.
  • Отсутствие lock у NameMapper.object_mappings — Отображение детерминировано; порча не установлена.
  • Пометка вместо удаления; guard по merged_on на каждую страницу — Обоснования (витрина видит только merged_on; самоблокировка группы между страницами) приняты; их пределы — CDC-04 и CDC-06.
Снятая гипотеза. Одинаковые Number/Year документов разных месяцев не доказывают частичный агрегат в примере витрины: source_condition применяется к уже агрегированной view с MAX(Period). Это не дефект реализации. Уникальность номера нужно согласовать с зерном витрины отдельно.

Условия, без которых гарантии ещё уже

До исправлений W1–W2 это не «советы», а фактические ограничения развёртывания.

  • Один активный репликатор на план обмена и один активный HandlerLoop на NAME — До исправления CDC-02 и CDC-09 это обязательное условие развёртывания.
  • Один часовой пояс сессий PostgreSQL без сезонного перевода — См. CDC-25. TZ контейнера на пояс сессии не влияет.
  • Env-режим без runner не сверяет удаления — Без расписаний FullLoadCron физические удаления и удаления независимых регистров не доедут никогда; в режиме once первичная выгрузка не запускается вовсе.
  • Дроссель обязателен на базах с толстыми пакетами — Ограничить SelectChanges с клиента нельзя; лимит дросселя — в объектах, а не в байтах (CDC-18).
  • pool_size ≥ full_load_workers + 3 + обработчики + расписания — Дефицит пула превращается в ложную «смерть» процесса (CDC-08), а не в ожидание.
  • Все ТЧ объектов плана включены в состав OData — Иначе первый же пакет с таким объектом блокирует план (CDC-20).
  • Имена объектов плана попарно различимы после транслита — Проверять до запуска (CDC-03).
  • Полная выгрузка вызывается только для владельцев, не для ТЧ — CDC-19.
  • Аналитика по сырым таблицам всегда фильтрует is_deleted_or_empty — Обнуление ресурсов — не гарантированная страховка (CDC-23).
