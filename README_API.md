# API: классы для настройки загрузки

Справочник описывает параметры и методы классов, используемых в скрипте запуска.
Внутренние компоненты — `DataReader`, `DBWriter`, `MetadataReader` — описаны в коде и
в [DESIGN.md](DESIGN.md).

Обзор и запуск — в [README.md](README.md), переменные окружения — в
[README_ENV.md](README_ENV.md), структура БД — в [README_DB.md](README_DB.md).
Готовый шаблон запуска — [config/runner.py](config/runner.py).

```python
from onecdc import Replicator, HandlerLoop, Handler, HandlerContext, FullLoadCron
```

`full_load` и `FullLoadCron` принимают имена объектов и полей как в 1С
(`Document_ЗаказКлиента`, `Дата`), так и в БД (`Document_ZakazKlienta`, `Data`).
Точные имена БД смотрите в `onecdc_metadata_objects.object_full_name_en` и `fields_en`:
при коллизиях и превышении длины они могут содержать хэш-суффикс.

В `Handler.ON` и `HandlerSignals` используются только имена **таблиц БД**.
Это важно и для подписки на изменения, и для расчёта окна обработчика.

## `Replicator` — чтение изменений и запись в БД

Оркестратор: читает изменения из 1С (OData + план обмена) и пишет их в целевую БД, подтверждая
приём пакета только после успешного сохранения. Этот же класс выполняет полную выгрузку.

```python
Replicator(
    odata_url: str,                       # адрес OData-интерфейса базы 1С
    odata_auth: tuple[str, str] | None,   # (пользователь, пароль); None — без авторизации
    engine: Engine,                       # готовый SQLAlchemy Engine, не строка подключения
    exchange_name: str | None = None,     # план обмена; без него — только полные выгрузки
    queue_guid: str | None = None,        # Ref_Key узла обмена; пустой — список узлов в лог
    db_schema: str | None = None,         # None — схема БД по умолчанию
    db_temp_schema: str | None = None,    # куда класть таблицы ключей выгрузки; None — схема данных
    request_timeout: float | None = None, # таймаут HTTP, сек; также принимается пара (connect, read)
    full_load_workers: int = 2,           # фоновых потоков полной выгрузки
    log_retention_days: int = 30,         # сколько держать журнал загрузок; 0 — хранить всё
    automatic_full_load: bool = True,     # назначать выгрузку новым объектам и при смене типа
    read_subconto: bool = False,          # субконто регистра бухгалтерии в JSON-колонку
    max_response_bytes: int | None = 512 * 1024**2,   # предел ответа 1С в байтах; None — без ограничения
)
```

Параметры проверяются в конструкторе: основные ошибки конфигурации обнаруживаются при создании объекта.
Конструктор подключается к БД и подготавливает служебные таблицы; чтение метаданных 1С
откладывается до первого обращения. `engine` передаётся готовым намеренно — пул задаёт приложение (см.
[README_DB.md](README_DB.md), «Сколько нужно соединений к БД»).

**Без `exchange_name`** репликатор умеет только полные выгрузки: план обмена им не нужен, а
`run_once`/`run_forever` откажутся стартовать. Так настраивают разовую загрузку и расписания — см.
[examples/full_load_once.py](examples/full_load_once.py).

`automatic_full_load=False` отключает автоматическое назначение выгрузки новым объектам
и при смене типа поля. Объекты с `full_load_is_required=true` фоновые потоки загружают
и при `False`. Прямой вызов `full_load` и расписания также продолжают работать.

| метод | что делает |
|---|---|
| `run_forever(interval=60.0, max_iterations=0, max_backoff=1800.0)` | цикл `run_once` с паузой `interval`, плюс фоновые выгрузки помеченных объектов. Блокирующий, останавливается по SIGTERM/SIGINT. Упавший цикл повторяется с нарастающей паузой |
| `run_once(notify_changes=True)` | один цикл: read → save → notify. `notify_changes=False` не подтверждает пакет — изменения остаются в очереди 1С, прогон повторяемый (удобно для проверки на реальной 1С) |
| `full_load(object_name, …)` | полная выгрузка объекта; возвращает число **реально изменённых** строк — ноль означает, что этот вызов не изменил строки или пропустил занятый объект. Параметры и поведение — ниже |
| `list_objects()` | что можно выгружать: документы, справочники и регистры из опубликованных метаданных. Это НЕ состав плана обмена: через изменения поступит только то, что есть в нём |
| `request_stop()` | попросить идущий `run_forever` завершиться после текущей итерации. Нужен, когда репликатор не в главном потоке: свой перехват сигналов ему там поставить нельзя |
| `claim_full_load(object_full_name)` | контекстный менеджер: занять объект на несколько шагов сразу. Ради одной выгрузки не нужен — `full_load` занимает его сам |

`request_timeout=None` выбирает таймауты по умолчанию: 60 секунд на соединение и
900 секунд ожидания данных при чтении. Это не предел длительности всего запроса.
Для подтверждения пакета используется отдельная пара таймаутов `(30, 30)`.

Для освобождения аренды узла после самостоятельной работы используйте `close()`;
`run_forever` вызывает его при штатном завершении. `close()` не останавливает активный цикл —
сначала вызовите `request_stop()` и дождитесь завершения.

### `full_load(object_name, batch_size=1000, date_field=None, date_from=None, date_to=None, mark_missing=True, read_subconto=None, skip_if_busy=True)`

| параметр | что делает |
|---|---|
| `batch_size` | максимальное число записей на странице; фактический размер подбирается с учётом объёма ответа |
| `date_field`, `date_from`, `date_to` | выгрузка за период с включительными границами; `date_to` типа `date` включает весь день, а `datetime` и ISO-строка задают точный момент. При наличии поля даты большие объекты автоматически читаются окнами |
| `mark_missing` | помечать строки, которых в 1С больше нет. По умолчанию **включено** |
| `read_subconto` | субконто регистра бухгалтерии; `None` — как задано у репликатора |
| `skip_if_busy` | при `True` занятый объект пропускается; при `False` возникает `FullLoadBusy` |

На время выгрузки объект захватывается в общей служебной таблице. Это координирует
фоновые потоки и скрипты в других процессах, использующих ту же целевую схему. Если объект занят,
вызов возвращает 0 и записывает `WARNING`. Чтобы отличить пропуск от завершённой выгрузки
без изменений, задайте `skip_if_busy=False`: при занятом объекте возникнет исключение.

Вызов использует реестр `onecdc_metadata_objects` для захвата объекта, но не снимает
`full_load_is_required` и не обновляет дату и метрики последней полной выгрузки. Эти поля
ведут фоновый поток и начальная загрузка истории в расписании (см. ниже).

При `mark_missing=True` строки, не прочитанные за весь прогон, помечаются отсутствующими.
Это не согласованный снимок: изменения источника во время `$skip` могут привести к пропускам
и временным ложным пометкам. Для независимых регистров планируйте повторные выгрузки
с перекрывающимися периодами. Подробности — [в DESIGN.md](DESIGN.md#пропавшие-строки-mark_missing).

Отключение `mark_missing` требует отдельного учёта удалений: сведения о физическом удалении
объекта не передаются через обмен. Без пометки строки останутся в таблице, а витрина не заметит
их исчезновения — она смотрит на `merged_on`. Поэтому `FullLoadCron` не позволяет отключать пометку.

## `Handler` — свой код по событию изменения

Базовый класс для расчёта витрины или отправки данных во внешнюю систему при изменении
таблиц, на которые подписан обработчик. Наследование необязательно: можно передать модуль с `ON` и `handle` или функцию
с атрибутом `ON`. Базовый класс предоставляет готовые методы для SQL-запросов.

```python
class ZakazyKlientov(Handler):
    ON = ["AccumulationRegister_ZakazyKlientov"]   # имена ТАБЛИЦ, не объектов 1С; список, не строка

    def handle(self, context: HandlerContext) -> None:
        self.execute(context, 'insert into ... where merged_on > :last_run_at',
                     last_run_at=context.last_run_at)
```

Аннотация `context: HandlerContext` не обязательна, но с ней IDE подсказывает поля контекста и их
типы — писать её стоит везде.

| объявление | смысл |
|---|---|
| `ON` | все таблицы, которые читает обработчик: по ним определяются сигналы и безопасная граница окна. Обязательно |
| `NAME` | имя в `onecdc_handlers`; по умолчанию имя класса. ключ состояния: обработчики с одинаковым именем используют общую отметку |
| `ON_FULL_LOAD` | вызывать ли на страницах полной выгрузки (по умолчанию да). `False` — для обработчиков, которым не нужны сигналы полной выгрузки: рассылок, отправки в очередь. Подробности ниже |
| `MIN_INTERVAL` | не чаще одного прогона в N секунд |

`ON_FULL_LOAD=False` отключает и сигналы о пометке исчезнувших строк: их обнаруживает полная
выгрузка. Пометка обновляет `merged_on`, а `last_run_at` ожидающего обработчика не меняется.
Поэтому эти строки остаются в его окне и будут обработаны при следующем сигнале от CDC.
Пометка на удаление в 1С (`DeletionMark`) передаётся как обычное изменение.

| метод | когда вызывается |
|---|---|
| `setup(context)` | один раз за процесс, до первого прогона: DDL витрины, создание представлений |
| `handle(context)` | обычный прогон за окно `(last_run_at, boundary]`. Обязателен |
| `rebuild(context)` | необязательный генератор полной пересборки: `yield <метка>` означает «блок закончен», между блоками библиотека применяет накопившиеся изменения. Не объявлен — пересборка идёт одним проходом |

Базовый класс также предоставляет методы для работы с БД:
`changed_since(context, *columns)` — условие «изменилось за окно» для SQLAlchemy;
`execute(context, sql, **params)` и `query(context, sql, **params)` — SQL с параметрами на движке
контекста (первый выполняет запрос, второй возвращает строки).

Методы принимают **готовый SQL** и связывают значения параметров, но не подставляют имя схемы.
Обработчик указывает схему сам, например с помощью f-строки. Для этого удобно собирать запрос
в функции, которая принимает контекст:

```python
def ddl(context: HandlerContext) -> str:
    schema = context.schema or 'public'          # пример использует public, если схема не задана
    return f'''
    CREATE OR REPLACE VIEW "{schema}"."ZakazyKlientov_view" AS ...
    '''
```

При сборке SQL действуют обычные правила f-строк: буквальные фигурные скобки нужно удваивать,
например в JSON или квантификаторе регулярного выражения `[0-9]{3}`. Значения данных передавайте
параметрами: `:name` вместе с `**params` или `.bindparams(...)`, если SQL-фрагмент
будет частью другого запроса.

В SQLAlchemy `text()` двоеточие может обозначать начало параметра. Поэтому JSON-литерал
записывают `'{"k"\:1}'` или с пробелом после двоеточия.

Готовые примеры обоих видов — в [config/handlers/](config/handlers/).

Данные обработчику **не передаются**: он получает окно по часам БД и выбирает изменившееся сам.
Как это работает и что нужно знать, чтобы витрина считалась правильно, — в docstring модуля
`onecdc.handlers`, а механика (сигнал, граница окна, пересборка блоками) — в
[DESIGN.md](DESIGN.md#обработчики-сигнал-окно-и-пересборка).

### `HandlerContext` — что обработчик получает

| поле | значение |
|---|---|
| `engine`, `schema`, `temp_schema` | подключение и схемы (те же, что у `HandlerLoop`) |
| `last_run_at`, `boundary` | границы окна: `(last_run_at, boundary]` — за него обработчик и отвечает. Обе всегда `datetime`: первый прогон и пересборка получают в `last_run_at` служебную начальную дату (`EPOCH`, 1900-01-01 UTC), а не `None` |
| `full_rebuild`, `rebuild_from` | идёт ли пересборка и метка последнего завершённого блока |
| `lease_is_mine` | SQL-условие владения именем обработчика для `source_condition`/`delete_condition`. Проверяет аренду в снимке SQL-оператора, но не удерживает её до коммита и не защищает внешние действия |
| `objects`, `sources` | диагностический контекст: `objects` содержит всю подписку `ON`; `sources` — причины запуска (`startup`, `db_signal`, `full_rebuild`). По ним нельзя определить конкретные изменившиеся строки или отличить CDC от полной выгрузки; данные выбираются по окну |
| `logger` | логгер обработчика |

## `HandlerLoop` — цикл одного обработчика

Запускает обработчика: следит за меткой сигнала в `onecdc_handlers`, считает окно, вызывает `handle` и
записывает результат. На каждого обработчика заводится свой цикл, поэтому тяжёлая витрина не
задерживает остальные.

```python
HandlerLoop(
    engine: Engine,
    schema: str | None,
    handler,                              # экземпляр Handler, модуль или функция
    temp_schema: str | None = None,       # передаётся в контекст; OneCDC не использует для staging
)
```

Есть ещё служебный `write_tracker` — цикл заводит его себе сам, задавать нужно только в тестах.

| метод | что делает |
|---|---|
| `run_forever(poll_interval=1.0)` | блокирующий цикл, как у репликатора; останавливается тем же SIGTERM |
| `run_if_pending()` | один прогон, если есть непрочитанный сигнал. Для своего планировщика или тестов |
| `request_stop()` | остановиться после текущего прогона |

Репликатор и обработчики обмениваются сигналами через таблицу `onecdc_handlers`.
Благодаря этому обработчики могут работать в отдельном процессе или контейнере.

## `FullLoadCron` — полная выгрузка по расписанию

По crontab-расписанию запускает `full_load` одного объекта. Такой цикл подходит для
первоначальной загрузки и периодической сверки данных, в том числе объектов вне плана обмена.
Ненулевой результат означает, что выгрузка изменила строки; причиной могут быть новые данные,
задержка CDC, удаление или ранее пропущенные изменения.

```python
FullLoadCron(
    replicator,                           # тот же Replicator — он исполнитель выгрузки
    table_name: str,                      # имя ТАБЛИЦЫ (латиница); имя 1С тоже принимается
    *,
    cron: str,                            # обычная crontab-строка; время локальное (см. TZ)
    date_field: str | None = None,        # поле даты для фильтра по периоду
    date_from=None, date_to=None,         # границы: дата, дата-время, ISO-строка или timedelta
    batch_size: int = 1000,
    full_history_on_first_run: bool = True,
)
```

`timedelta` в границе даёт скользящее окно: `date_from=timedelta(days=3)` — «последние трое суток»,
считается в момент срабатывания. Целые сутки отсчитываются от сегодняшней **даты** (то есть с
полуночи — ночное «перечитать неделю» берёт неделю целиком), смещение меньше суток или с остатком —
от текущего **момента**: иначе `timedelta(hours=12)` дало бы сегодняшнюю дату, и окно оказалось бы
пустым.

Граница типа `datetime` должна быть **без часового пояса**: 1С хранит даты без поясов, и aware-datetime
отвергается с ошибкой. Доли секунды усекаются — 1С их всё равно не принимает, а область пометки
пропавших строк обязана совпадать с областью чтения. Объект, который уже выгружается (фоновая
выгрузка репликатора или другое расписание), пропускается с предупреждением.

| метод | что делает |
|---|---|
| `run_forever(max_runs=0)` | блокирующий цикл по расписанию |
| `run_once()` | выполнить выгрузку немедленно, используя настройки расписания |
| `request_stop()` | остановиться после текущего прогона |

`full_history_on_first_run=True` действует, если задана хотя бы одна граница периода
и в реестре ещё нет `last_full_load_dt`. Такой прогон игнорирует границы и после успеха
отмечает объект полностью загруженным. Расписание без границ и обычные последующие прогоны
не обновляют дату и метрики полной выгрузки в реестре.

Каждое расписание работает в отдельном потоке. При расчёте предела пула
(`pool_size + max_overflow`) добавляйте по одному соединению на расписание.
