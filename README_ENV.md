# Запуск из окружения: переменные `ONECDC_*`

В этом режиме OneCDC запускается **без пользовательского Python-кода**: параметры задаются
переменными окружения. Запускается командой `onecdc` либо как модуль:

```bash
onecdc
python -m onecdc     # то же самое
```

В контейнере это поведение по умолчанию: не смонтирован `/config` со своим `runner.py` — работает
именно этот режим (см. [README](README.md), «Запуск в Docker»).

## Что этот режим умеет и чего не умеет

Готовая точка входа использует `Replicator`: читает изменения из 1С через OData и план обмена и
пишет их в целевую БД, подтверждая приём пакета только после успешного сохранения. В режиме
`loop` — плюс полные выгрузки объектов, которые встали в очередь (новый объект, заказанная
перевыгрузка): их раздаёт фоновым потокам сам цикл. В режиме `once` этого шага нет — одиночный
проход только помечает такие объекты, а выгрузит их следующий запуск в `loop` (или ваш вызов
`full_load`).

Для следующих сценариев нужен собственный скрипт запуска:

- **обработчики** (витрины поверх загруженных таблиц) — их классы надо где-то написать;
- **полные выгрузки по расписанию** (`FullLoadCron`) — состав расписаний тоже задаётся кодом;
- **несколько планов обмена** в одном процессе.

Понадобилось что-то из этого — берите шаблон [config/runner.py](config/runner.py): в нём приведены примеры
подключения обработчиков и расписаний. Для нескольких планов создайте отдельный `Replicator`
на каждый узел и добавьте его цикл в список запускаемых задач. Шаблон также читает окружение,
но проверяет значения иначе, чем команда `onecdc` (см. ниже).

## Переменные

### Обязательные

| Переменная | Значение |
|---|---|
| `ONECDC_ODATA_URL` | адрес OData-интерфейса базы 1С, например `http://server/base/odata/standard.odata` (именно интерфейса, а не базы) |
| `ONECDC_EXCHANGE_NAME` | имя плана обмена в 1С — то, что видно в конфигураторе |
| `ONECDC_DB_URL` | строка подключения SQLAlchemy к целевой БД, например `postgresql+psycopg2://user:pass@host:5432/dwh` |
| `ONECDC_QUEUE_GUID` | `Ref_Key` узла обмена (очереди) |

`ONECDC_QUEUE_GUID` формально можно не задавать: чтение изменений тогда выведет в лог список узлов
плана обмена и завершит цикл с ошибкой — GUID можно скопировать из журнала. Чтение списка требует доступа к 1С.
В режиме `loop` ошибочный цикл будет повторяться; остановите процесс и задайте найденный GUID.

### Необязательные

| Переменная | По умолчанию | Значение |
|---|---|---|
| `ONECDC_ODATA_USER` | — | пользователь OData; не задан — запросы идут без авторизации |
| `ONECDC_ODATA_PASSWORD` | пусто | пароль этого пользователя. Кириллица допустима: заголовок авторизации отправляется в UTF-8. По `http://` пароль уходит открытым текстом — при старте об этом предупреждают в логе |
| `ONECDC_DB_SCHEMA` | схема БД по умолчанию (`public` у Postgres) | схема, в которой создаются таблицы данных |
| `ONECDC_DB_TEMP_SCHEMA` | схема данных | куда класть одноразовые таблицы ключей полной выгрузки |
| `ONECDC_FULL_LOAD_WORKERS` | `2` | число фоновых потоков полной выгрузки |
| `ONECDC_AUTOMATIC_FULL_LOAD` | `true` | назначать ли полную выгрузку новым объектам и при смене типа поля; `false` не отменяет уже назначенные выгрузки |
| `ONECDC_POLL_INTERVAL` | `60` | пауза между успешными циклами чтения изменений, секунд (только в режиме `loop`) |
| `ONECDC_MODE` | `loop` | `loop` — непрерывный цикл; `once` — один цикл read → save → notify и выход |
| `ONECDC_LOG_LEVEL` | `INFO` | `DEBUG` / `INFO` / `WARNING` / `ERROR` / `CRITICAL` |
| `ONECDC_LOG_RETENTION_DAYS` | `30` | сколько суток держать журнал загрузок (`onecdc_replicator_log`); `0` — хранить всё |
| `ONECDC_RUNNER` | `/config/runner.py` | **только в контейнере**: путь к собственному скрипту запуска |

Про `ONECDC_DB_TEMP_SCHEMA` стоит сказать отдельно: своя схема удобна тем, что таблицы ключей отделены от таблиц данных. Это упрощает
поиск таблиц, оставшихся после аварийной остановки процесса. Промежуточную таблицу самого merge эта схема не касается —
`dbmerge` заводит её настоящей `TEMPORARY` (подробнее в [README_DB.md](README_DB.md)).

`ONECDC_FULL_LOAD_WORKERS` влияет и на пул соединений: entrypoint заводит `create_engine` с
`pool_size=3, max_overflow=ONECDC_FULL_LOAD_WORKERS` — соединение держат цикл изменений и страницы
полной выгрузки (подробнее — [README_DB.md](README_DB.md), «Сколько нужно соединений к БД»).

Смонтированный `runner.py` читает те же переменные, кроме `ONECDC_MODE`: что и как запускать,
определяет код скрипта. (`ONECDC_RUNNER` читает тоже не он, а контейнер — чтобы его
найти.) Пул он считает от числа своих обработчиков и расписаний.

`ONECDC_AUTOMATIC_FULL_LOAD=false` отключает автоматическое назначение полной выгрузки
новым объектам и при смене типа поля. Объект, помеченный руками в `onecdc_metadata_objects`,
контейнер выгрузит по-прежнему. Это полезно, если первая загрузка назначается на стороне 1С
(см. [README.md](README.md), «Полная (первоначальная) выгрузка»).

### Часовой пояс

| Переменная | Значение |
|---|---|
| `TZ` | часовой пояс процесса, например `Europe/Moscow` |

В контейнере время по умолчанию UTC. На чтение изменений это не влияет, но расписания
`FullLoadCron` считаются в локальном времени, поэтому для расписаний задайте `TZ`, если нужен часовой пояс, отличный от UTC.

## Проверка параметров и ошибки

Команда `onecdc` проверяет обязательные переменные, числа, флаги, режим и уровень логирования.
Срок хранения журнала — целое число от нуля; число потоков и интервал опроса должны быть
положительными. Ноль в `ONECDC_LOG_RETENTION_DAYS` отключает очистку журнала.
Флаги принимают `true/false`, `1/0`, `yes/no`, `on/off` без учёта регистра.

Ошибки разбора окружения выводятся одной строкой:

```text
ONECDC_ODATA_URL is not set (required: ONECDC_ODATA_URL, ONECDC_EXCHANGE_NAME, ONECDC_DB_URL)
ONECDC_POLL_INTERVAL='xx' is not a number
ONECDC_FULL_LOAD_WORKERS='-1' must be positive
ONECDC_LOG_RETENTION_DAYS='-1' must be non-negative
ONECDC_AUTOMATIC_FULL_LOAD='da' is not a flag (expected true/false)
Unknown ONECDC_MODE='step' (expected 'loop' or 'once')
Unknown ONECDC_LOG_LEVEL='TRACE' (expected DEBUG/INFO/WARNING/ERROR/CRITICAL)
```

Не все проверки выполняются до подключения к БД: например, уровень логирования проверяется
после создания `Replicator`, а интервал — перед запуском цикла. Ошибки параметров, обнаруженные
внутри библиотеки, могут сопровождаться traceback.

Недоступность БД при старте и сетевые ошибки 1С в режиме `once` выводятся кратким сообщением.
В режиме `loop` ошибки чтения записываются в журнал, а цикл повторяется с увеличенной паузой.
Пароль в адресе БД в сообщении о подключении скрывается.

Шаблон `config/runner.py` — самостоятельный Python-скрипт. Он использует `int` и `float`
для чисел, а ложными значениями флага считает `0`, `false`, `no`, `off`; остальные строки
включают флаг. Сообщения об ошибках могут отличаться от команды `onecdc`.

Параметры `request_timeout`, `read_subconto` и `max_response_bytes` не имеют переменных
`ONECDC_*` в готовой точке входа. Для их изменения передайте аргументы `Replicator`
в собственном скрипте.

## Примеры

Локально, разовая проверка доступов (один цикл и выход):

```bash
ONECDC_ODATA_URL="http://server/base/odata/standard.odata" \
ONECDC_ODATA_USER=odata ONECDC_ODATA_PASSWORD=secret \
ONECDC_EXCHANGE_NAME="ДляODATA" \
ONECDC_QUEUE_GUID="a9bc23c5-3689-11f1-926c-0800270bc6cb" \
ONECDC_DB_URL="postgresql+psycopg2://user:pass@localhost:5432/dwh" \
ONECDC_DB_SCHEMA=onecdc ONECDC_DB_TEMP_SCHEMA=onecdc_tmp \
ONECDC_MODE=once \
onecdc
```

В контейнере те же переменные передаются ключами `-e` либо перечисляются в
[docker-compose.yml](docker-compose.yml) — там к каждой есть комментарий, и настройка читается
одним экраном. Полные команды запуска — в [README](README.md), раздел «Запуск в Docker».
